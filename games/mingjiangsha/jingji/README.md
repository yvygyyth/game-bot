# 竞技场（名将杀）

四步跳转，**四种状态全部认得出**：

```
首页 ──点「竞技」──▶ 竞技场 ──「创建队伍」──▶ ──「添加伙伴」──▶ ──「开始匹配」──▶ 匹配中
      (home.png)      (jingji.png)          (add-pet.png)      (start.png)
```

```bash
python -m games check    mingjiangsha/jingji   # 静态自检（不需要游戏）
python -m games probe    mingjiangsha/jingji   # 真机探针：现在屏幕上认得出哪一页
python -m games setup    mingjiangsha/jingji   # 抓一张参考画面给自检用
```

真机探针的实际输出：

```
真机探针：抓一张当前画面……
  画面 1918x1080（客户区）
  ✓ 认出来了：**首页**（竞技入口在 (1008,456)，分数 0.983，偏离期望 3 像素）
```

```
--- add-pet.png ---   ✓ 竞技场  标题 1.000   已建队（添加伙伴 1.000）
--- start.png ---     ✓ 竞技场  标题 1.000   可以匹配（开始匹配 1.000）
```

## 关键设计：一个节点 + 顺序探测，而不是三个节点三条边

竞技场的三个状态**是同一个页面** —— 页面标识（左上角「竞技场」标题）
在三种状态下都是 **1.000**，也就是说页面树区分不了它们。

那就要在同一个页面上表达三段行为：

* 画三个节点、用边串起来 —— 但三个节点的 `page` 都是 `home/jingji`，
  位置守卫对它们一视同仁，"现在该在第几段"得靠额外条件判断，反而绕；
* **一个节点 + 一个按顺序探测的步骤**（选的这个）—— 把"该点哪个"交给游戏自己：
  哪个按钮在就点哪个。状态机在游戏那边，脚本不需要重复维护一份。

而且更抗状态错位：万一某一步没生效，下一轮照样接着往下走，不会卡死在某个节点上。

### 顺序不能变，有实测依据

**「开始匹配」在三个状态下都在** —— 它从进竞技场就可见（只是没队伍时是灰的）。
所以顺序探测里它必须排最后，否则第一轮就直接点它了。

自检里那张表就是验这件事的：

```
        状态        创建队伍        添加伙伴        开始匹配   会点哪个
  jingji.png       1.000       0.690       0.999   create_team   ✓
 add-pet.png       0.683       1.000       0.487   add_pet       ✓
   start.png       0.667       0.671       1.000   start_match   ✓
```

（`开始匹配` 在 add-pet 状态下只有 0.487 —— 那按钮是**灰的（禁用态）**。
不影响顺序探测，而且意味着"漏认 添加伙伴"时它也不会被点，行为是安全的。）

## 三轮测量才定下来的事

### ① 首页竞技卡：悬浮不是"渲染不同"，是**位移 + 放大**

我一开始拿你早期给的三张图测，得到 0.822/0.782/0.647，还以为是"悬浮重绘了像素"。
拿到 `home.png` 逐项量之后才看清：

| | 客户区偏移 | 卡片位置 | 位移 | 缩放 | 空闲模板的分数 |
|---|---|---|---|---|---|
| `home.png`（悬浮） | (1, 31)，底栏 0.995 | (932,279) | **(+27,−41)** | **1.100** | **0.774** |

卡片是**向右上弹了 27/41 像素并放大 1.10 倍**。金字塔本来就能吃 1.10 倍缩放
（它正好命中 1.100 那一档），掉分全来自位移导致的重叠变少。

顺手排除掉的四个错误猜测（都实测过，全是否）：尺度（1.00~1.02 达峰，
2% 尺度误差只值 0.07 分）、JPEG（q70 还有 0.996）、往返重采样（0.991）、
亮度对比度（128vs124 / 73vs76，几乎一样）。

**结论：一个模板 + ROI + 阈值 0.55 就够**（悬浮 0.774 ≫ 0.55，非首页 ≤0.439）。
所以我之前做的那个"悬浮模板"删掉了 —— 它是用一个误判的原因做出来的。

### ② 页面标识不能用会随状态变的东西

| 能不能用 | 理由 |
|---|---|
| ✅ 左上角「竞技场」标题（148x52） | 三种状态下都是 1.000 |
| ❌ 右侧队伍面板 | 三种状态长得完全不同（空位+创建队伍 / 空位+添加伙伴 / 两个头像+开始匹配）。用它当页面特征，**走到第二步就认不出自己在哪一页了** |
| ❌ 背景 | 竞技场背景是**活的** —— 骑马那角色披风一直在飘，三张图背景像素完全不同。模板框进背景，换一帧就废 |

### ③ 按钮的位置一样、只有文字不同

「创建队伍」和「添加伙伴」在**同一个位置**（客户区 1644,659，195x55），
只有文字不一样。所以它们靠文字区分，余量 0.31（1.000 vs 0.683/0.690）——
足够，但这也是为什么阈值不能给太低。

## 关于 assets/ 那四张图

它们是**本地参考素材，不入库**（14MB）。自检在没有它们时会跳过"资产图回归"
那一项，其余检查照常。模板（运行期真正要用的那几张几十 KB 的小图）是入库的。

重新生成模板（换分辨率或游戏改版之后）：

```bash
uv run python logs/tools/build_jingji_templates.py
```

那个脚本会顺便量分：每个模板在自己的图上必须 1.0，并打印顺序探测那张表。
