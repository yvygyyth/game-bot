# 竞技场（名将杀）

四步跳转：

```
首页 ──点「竞技」──▶ 竞技场 ──「创建队伍」──▶ ──「添加伙伴」──▶ ──「开始匹配」──▶ 匹配中
```

```bash
uv run python -m games check    mingjiangsha/jingji   # 定义对不对、缺哪些图
uv run python -m games describe mingjiangsha/jingji   # 状态树 + 流程图长什么样
uv run python -m games run      mingjiangsha/jingji --dry-run --max-ticks 20
```

## 怎么确认"现在认得出哪一页"

**跑一次**（`games run <脚本> --dry-run --max-ticks 20`），然后看界面上的
「**识图日志**」：记录器把每次匹配的框画在真机的截图上
（**红=命中、橙=未命中、蓝=搜索范围**），旁边还有一张结构化表格
（查了什么、在哪块搜、几分、中没中）。认没认出来、认的是哪一块、位置偏没偏，
一眼就看出来。

早先这里有三套手动验证的东西，**都删掉了**：

* `games selftest`（静态自检）—— 每个脚本要抄一份、又没人维护；
* `games probe`（真机探针）—— 输出不如一张带框的图直观；
* 界面上的「抓一张」—— 和上面那个一样，只是点一下就跑一遍识别。

现在**只有一条路**：真的跑起来，用识图日志看它认到了什么。
这也更接近实际 —— 识别是在真跑的过程中发生的，单独"抓一帧试试"
跟真跑时的帧、ROI、帧新鲜度都不完全一样。

## 关于 assets/ 那四张图（已废弃）

曾经放过四张真机截图（`home.png` / `jingji.png` / `add-pet.png` / `start.png`），
自检拿它们做"资产图回归"。**连同那一项一起删了**，图也可以删（14MB）。

原因：那四张图不入库、没人维护，而检查项在目录不存在时报的是「✓ 跳过」——
**打绿勾**。加新脚本时你会看到一个勾，以为验过了，其实一张样本都没有。
"没样本也算过"的检查比没有检查更糟。

真要做图像回归，正确做法是写成 `tests/` 里的测试、样本随测试入库。

模板（运行期真正要用的那几张几十 KB 的小图，在 `templates/`）是**入库**的，
和 assets 无关。

## 可调的运行参数（`form.py`）

四个值从代码里搬到了表单上 —— 它们全都是"同一次跑和下一次跑可以不一样"的东西，
写死的代价是**每调一次都要改代码、重启、重跑**：

| 参数 | 默认 | 为什么要能调 |
|---|---|---|
| `jingji.rounds` | 1 | 刷几轮 |
| `jingji.settle` | 1.0 | 点完等多久。网络慢/机器卡就调大 —— 硬编码的时间不是太短就是太长 |
| `jingji.confidence` | 0.85 | 按钮阈值。实测自己的图上 1.000、按钮之间最高 0.690，所以 0.85 余量大；误认就调高，认不出就调低 |
| `jingji.strict` | False | 严格模式。调脚本时想看"认不出来就停" |

**它们不在步骤的构造函数里**，而是步骤 `run()` 时用
`ctx.param("jingji.settle", ...)` 现读。原因是步骤在 `build_scenario()` 里构造、
那时拿不到表单值 —— 详见 `games/README.md` 的"运行参数的表单"。

界面上是右上角那块（四个控件 + 重置按钮）。命令行同样能覆盖：

```bash
uv run python -m games run mingjiangsha/jingji --param jingji.rounds=3 --param jingji.strict=true
```

两条路走**同一个** `FORM.fill()` 做校验 —— 所以不会出现"界面拦得住的、
命令行拦不住"。

## 关键设计：三个状态 = **三个页面状态**，一个状态一个节点

### 原来是"一个节点 + 顺序探测"

竞技场的三个阶段最初**算同一个页面**：页面标识（左上角「竞技场」标题）在三种状态
下都是 **1.000**，页面树区分不了它们。所以那时只能画一个节点、一个按顺序探测
三个按钮的步骤，"该点哪个"交给游戏自己。

那样能跑，但有两个代价：日志里"三个按钮一个都没看到"分不清是哪个没认出来；
``describe`` 里也看不出走到第几段。

### 现在：`home/jingji` 是分类节点，下面是三个并列子状态

```
home/jingji                        竞技场（分类节点：不匹配、只提供 ROI）
├── home/jingji/before_create      右下角是「创建队伍」
├── home/jingji/after_create       右下角是「添加伙伴」
└── home/jingji/after_add          右下角是「开始匹配」
```

**区分它们的是右下角那个按钮**，不是标题 —— 这是这次改动能成立的关键：
标题三者相同（所以它不再是页面标识），按钮三者不同。

于是每个状态可以有自己的节点和步骤，位置守卫天然生效（不会在错误的阶段点错的
按钮），日志能说清是哪个按钮没认出来。

### 这组实测分数就是"能不能拆"的依据

当初量过三张按钮图彼此的分数：

```
        状态        创建队伍     添加伙伴     开始匹配   会点哪个
  jingji.png       1.000      0.690      0.999    create_team
 add-pet.png       0.683      1.000      0.487    add_pet
   start.png       0.667      0.671      1.000    start_match
```

* **对角线全是 1.000**（自己认自己）；
* **交叉最高 0.690** —— 而阈值取 0.85，余量 0.16。所以三个状态**区分得开**，
  这是拆成三个子状态的前提（有测试 ``tests/test_jingji_states.py`` 钉着）；
* ``add-pet.png`` 状态下"开始匹配"只有 **0.487** —— 因为那按钮是**灰的
  （禁用态）**。这条很重要：它说明 :data:`~.advance_team.T_START_MATCH` 那张图
  **必须是亮态截的**。若哪天它被换成灰态图，``home/jingji/after_add``
  就永远认不出来。

### `start_match` 在三态都可见，为什么现在不成问题

旧设计里"三个按钮都可见"是个麻烦（顺序探测必须把它排最后，否则第一轮就点它）。
现在它反而是**好消息**：正因为按钮可见、只是亮暗不同，它的**亮态**才能当
"加完伙伴"这个状态的唯一特征。

> ``start_match.png`` 尺寸 265x65，比另外两张（195x55）大 —— 那正是"亮态"
> 的视觉差异（灰态和亮态的字号/描边不同）。这个差异是设计依赖，不是巧合。


## 三轮测量才定下来的事

### ① 首页竞技卡：悬浮不是"渲染不同"，是**位移 + 放大**

我一开始拿你早期给的三张图测，得到 0.822/0.782/0.647，还以为是"悬浮重绘了像素"。
拿到 `home.png` 逐项量之后才看清：

| | 客户区偏移 | 卡片位置 | 位移 | 缩放 | 空闲模板的分数 |
|---|---|---|---|---|---|
| `home.png`（悬浮） | (1, 31)，底栏 0.995 | (932,279) | **(+27,−41)** | **1.100** | **0.774** |

卡片是**向右上弹了 27/41 像素并放大 1.10 倍**。金字塔本来就能吃 1.10 倍缩放
（它正好命中 1.100 那一档），掉分全来自位移导致的重叠变少。

顺手排除掉的四个错误猜测（都实测过，全是否）：尺度（1.00~1.02 达峰，
2% 尺度误差只值 0.07 分）、JPEG（q70 还有 0.996）、往返重采样（0.991）、
亮度对比度（128vs124 / 73vs76，几乎一样）。

**结论：一个模板 + ROI + 阈值 0.55 就够**（悬浮 0.774 ≫ 0.55，非首页 ≤0.439）。
所以我之前做的那个"悬浮模板"删掉了 —— 它是用一个误判的原因做出来的。

### ② 页面标识不能用会随状态变的东西

| 能不能用 | 理由 |
|---|---|
| ✅ 左上角「竞技场」标题（148x52） | 三种状态下都是 1.000 |
| ❌ 右侧队伍面板 | 三种状态长得完全不同（空位+创建队伍 / 空位+添加伙伴 / 两个头像+开始匹配）。用它当页面特征，**走到第二步就认不出自己在哪一页了** |
| ❌ 背景 | 竞技场背景是**活的** —— 骑马那角色披风一直在飘，三张图背景像素完全不同。模板框进背景，换一帧就废 |

### ③ 按钮的位置一样、只有文字不同

「创建队伍」和「添加伙伴」在**同一个位置**（客户区 1644,659，195x55），
只有文字不一样。所以它们靠文字区分，余量 0.31（1.000 vs 0.683/0.690）——
足够，但这也是为什么阈值不能给太低。

## 还没做的：匹配中那一页

点完「开始匹配」之后会进匹配队列，**那一页我还没有截图**，所以流程到这里结束：
`jingji` 是末梢节点（没有出边），队伍三步推完之后它只会 `not_found`，引擎连着
几轮之后判定 **`no_more_work`（流程走到头了）** 并正常停下，日志里留一条 warning。

**这比瞎猜下一个节点好** —— 不知道去哪就不动，是这套设计一直在守的规矩。
补一张匹配页的截图，加一个 `Page`、一个 `Node`、一条 `on_page` 边就接上了
（那时 `jingji` 有出边了，这条判定也不会再触发）。

重新生成模板（换分辨率或游戏改版之后）：

```bash
uv run python logs/tools/build_jingji_templates.py
```

那个脚本会量分：每个模板在自己的图上必须 1.0，并打印顺序探测那张表。
**它是调试脚本，不是自动检查** —— 早先有个自检项替它做这件事（"资产图回归"），
已经删了（原因见上）。要长期保住"模板没裁歪"，得把它挪成 `tests/` 里的测试。
