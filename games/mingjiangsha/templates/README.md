# 名将杀 · 游戏级公共模板

跨脚本共用的图放这里。查找顺序是 **功能级优先、本目录兜底**：

```
games/mingjiangsha/scripts/<功能>/templates/   ← 先找（可以覆盖同名图）
games/mingjiangsha/templates/                   ← 再找（公共按钮花纹）
```

## 按钮：**一个文件夹 = 一种按钮**

```
templates/gold_glow/     金色发光按钮：创建队伍 / 添加伙伴 / 确定 / 投降确认 …
templates/gold_frame/    金色花纹边框的大按钮：确定 / 开始匹配 / 开始对局 / 结算确认 …
templates/cyan_glow/      青色发光按钮：取消
templates/blue_frame/                蓝底金框按钮：下一步
```

> 同一家族里放的是**这种按钮的各种文字版本**（尺寸不同就再各存一张）。
> 因为只比边框环，不同文字版本会命中同一个位置；`find_buttons` 按位置去重，
> 所以"把家族里每张图都试一遍"不会歧义。

调用时**直接挑对应的方法**（四种按钮各一个入口，底层都只比边框环）：

```python
from games.mingjiangsha.utils import (
    click_gold_frame,
    click_blue_frame,
    click_cyan_glow,
    click_gold_glow,
)

click_gold_glow(ctx)    # 金色发光：创建队伍 / 添加伙伴 / 确定 / 投降确认
click_gold_frame(ctx)   # 金色花纹大按钮：选将确定 / 开始匹配 / 结算确认
click_cyan_glow(ctx)     # 青色：取消
click_blue_frame(ctx)           # 蓝底金框：下一步
```

> 底层还有通用的 `click_button(ctx, 家族名)`：给"确实要按名字动态选"的场合用
> （比如四选一按配置决定）。写脚本时优先用上面四个 —— 意图清楚、也少传一个字符串。

**加一种文字版本不用改代码**：裁一张这个按钮的图丢进对应文件夹即可。
**加一种新按钮**：新建文件夹，并在 `utils/buttons.py` 加一个对应的方法。

### 裁图约定

1. **完整包含按钮**（四周留 2~3 像素），别带按钮之外的大片背景 —— 背景会随界面变；
2. 同一家族里不同**文字**版本会**互相命中**（这正是"只比边框"的目的）——
   它们命中的是同一个位置，`find_buttons` 按位置去重；不同**尺寸**才要各存一张；
3. **一种按钮一个文件夹**。混进两种不同按钮会让 `pick="only"` 频繁报错。
4. **同一个按钮的多张截图版本可以共存**（比如不同分辨率各裁了一张）——
   它们会同时命中同一个按钮，`find_buttons` 按位置去重、只留分数最高的那张。
   但**同一批截图里尽量只留一套**：混着放会让日志里的分数忽高忽低，不好判断阈值。

### 匹配到底是怎么做的（换文字为什么也能中）

**每个文件是一整块按钮图，但比对时只比它的"边框环"** —— 遮罩中心，文字完全不参与。
环的参数是两个**游戏级常量**（`games/mingjiangsha/utils/buttons.py`）：

```python
BUTTON_RING_INSET = 4    # 从裁剪图外沿往里缩 4px 再取（跳过裁进来的背景）
BUTTON_RING_WIDTH = 12   # 环宽 12px
```

`click_button(ctx, 家族)` 做的事：

```
for 这个家族的每一张图:
    按它的尺寸生成边框环遮罩
    只在这个环内做"减均值相关"（不是整块比、也不是 OpenCV 的 masked CCORR）
合并命中 -> 同一个按钮（60px 内）只留分数最高的 -> 按 pick 挑一个
```

所以**中间的文字换了不影响**：

| 模板 | 目标 | 分数 |
|---|---|---|
| 创建队伍（225×82） | 自己那屏 | 0.998 |
| 创建队伍 | 同位置换成**添加伙伴**（同尺寸、换文字） | **0.997** |
| 确定（263×92） | 有确定的弹窗 | 0.991 |
| 取消（259×87） | 同一弹窗里的取消 | 0.996 |
| 上述模板在**没有这类按钮**的画面上 | — | 0.65~0.77 |

> 同一张弹窗上，「确定」的模板只命中确定的中心 (1075,953)，「取消」的模板只命中
> 取消的中心 (1474,953) —— 两个家族不会互相误点。

### 尺寸和分辨率仍然是硬的

环的四条边位置**跟着按钮尺寸走**，所以：

* **换文字** -> 一张模板就够（环完全一致）；
* **换尺寸**（确定 257×87 vs 添加伙伴 218×72）-> 仍然是两张模板，各比各的；
* **换分辨率** -> 环的位置就变了，**要按新分辨率重裁**。

注意 `find_all_images`（按钮用的就是它）是**单尺度**的：它不会把模板缩放去凑。
多尺度金字塔只服务于 `find_image`（状态锚点那条路），按钮这条不靠它。

## 为什么是"整个环"，而不是一条边线

试过：取一条 12×33 的竖边去匹配所有金框按钮。**裁剪图上**很漂亮，但在**整屏**上
命中 100 次 —— 面板边框、图标边缘全是"亮竖边"。

原因不是"边线不够像"，而是**一条边不构成约束**。改成**四条边一起比**（环），
形状就被钉死了；再加上**减均值**（OpenCV 自带的 masked CCORR 不减均值、被亮度主导，
亮度一高就是 0.98，整屏误命中），才把误命中压到 0。代价是要支持遮罩匹配 ——
这个能力已经加在 `OpenCvMatcher` 里了（`mask=` 参数）。

## 原始素材

`gold_glow/` 等目录里的图**同时**是运行期模板和重裁素材 ——
换分辨率/改版后，从这里挑一张重新裁即可。界面选脚本时的检查会把它们归到
"游戏级另有 N 张没被 `T_*` 声明（按钮家族按文件夹约定使用，不算错）"，
只有**功能级**里没声明的图才会被当成"该删的旧图"列出来。
