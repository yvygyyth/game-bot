# 状态仓库（跨运行的记忆）

**什么时候读这份**：脚本里有"下次开还该记得"的东西时 —— 背包、体力、累计局数、
上次领奖励是哪天。

一句话：**`ctx.blackboard` 活一次运行，`ctx.store(...)` 活到下次运行。**

源码：`src/gamebot/state/store.py`。这份文档讲**怎么用**和**为什么这么分**，
不重复源码里的实现细节。

---

## 一、三样"存东西的地方"，按寿命分

|  | 运行参数 | 黑板 | 仓库 |
|---|---|---|---|
| 是什么 | 这次运行的**输入** | 这次运行**跑出来的** | **跨运行**的记忆 |
| API | `ctx.param(...)` | `ctx.blackboard` | `ctx.store(SPEC)` |
| 关掉再开 | 还得重新填 | 没了 | **还在** |
| `reset()` | 不动 | 清空 | 不动 |
| 落盘 | 不落 | 不落 | `data/stores/<游戏>/<仓库 id>.json` |

判断只有两句：

1. **"用户还没点开始时它就有值了吗？"** 有 → 参数；
2. **"下次开还该记得吗？"** 该 → 仓库；不该 → 黑板。

`jingji` 里两句话都用上了：`jingji.rounds`（这次刷几局）是参数，
`fight.rounds`（这次已经刷了几局）是黑板，`jingji.runs`（历史上总共刷了几局）
是仓库。**同一个"局数"，三种寿命，三个地方。**

---

## 二、一个脚本可以用好几个仓库

不要把所有东西塞进一个 `bag`。背包、体力、累计局数是**三件事**：
它们的寿命不同、坏一文件不该连累别的、界面上也该分组显示。

所以：**一个仓库一个声明**，用 `define_store` 写。

```python
# games/mingjiangsha/scripts/jingji/store/runs.py
from gamebot.state.store import define_store

RUNS = define_store(
    "jingji.runs",                                   # id：全局唯一 + 落盘文件名
    title="累计局数",                                  # 界面/日志里显示的名字
    defaults={"done": 0, "last_finished_at": ""},     # 第一次开的样子
    help="跨运行累计；关掉界面再开也不会归零",
)
```

步骤里取它：

```python
from ..store import RUNS

def finish_round(ctx):
    ctx.store(RUNS).bump("done")
```

> 同一个 id 在同一次运行里多次 `ctx.store` 拿到的是**同一个对象**；
> 但两次运行之间靠磁盘上那个 JSON 传递，不是靠进程里的对象活着。

---

## 三、放在哪：`store/` 目录，一个仓库一个文件

和 `steps/` 是同一套组织方式：

```
games/<游戏>/
├── store/                       ← 游戏级：多个脚本都能 import
│   ├── __init__.py              ←   只做转发（from .bag import BAG）
│   └── bag.py                   ←   背包
└── scripts/<功能>/
    └── store/                   ← 功能级：只有这个脚本用
        ├── __init__.py
        └── runs.py              ←   累计局数
```

**放哪一级的判断**：第二个脚本会不会原样用它？会 → 游戏级；不会 → 功能级
（默认放功能级，提到游戏级是加法）。

**id 的写法**：

| 位置 | 写法 | 落盘 |
|---|---|---|
| 游戏级 | `"bag"` | `data/stores/<游戏>/bag.json` |
| 功能级 | `"jingji.runs"` | `data/stores/<游戏>/jingji.runs.json` |

功能级必须带功能前缀 —— 同一游戏的两个脚本都会有 `runs`，不隔开会互相覆盖。
文件名与 id 的**最后一段**一致（`runs.py` ↔ `"jingji.runs"`）。

---

## 四、刻意不做 schema 校验

仓库**不检查**"这个 key 该不该存在"。背包里的东西每周都在变，逼着人先声明字段，
等于把"改一行代码"变成"改声明 + 重启 + 迁移旧数据"。

代价：**字段名拼错不会报错**（会多出一个 key）。这是有意的取舍 ——
仓库的价值是"下次开还在"，不是"帮我检查脚本"。

要强约束的东西放**运行参数**（`form.py` 有表单校验）。
`defaults` 只是"第一次开的样子"，不是白名单：文件里有、声明里没有的 key 会
原样保留（那是别人写进去的数据，不能静默删掉）。

---

## 五、落盘

* 每个仓库一个 JSON：`data/stores/<游戏>/<仓库 id>.json`；
* 写成 **临时文件 + `os.replace`**（原子）：写一半断电不会留下半个 JSON；
* **坏文件不挡开跑**：解析失败就改名成 `<名字>.corrupt-<时间戳>.json` 留证据，
  然后从默认值开始 —— "记忆丢了"能忍，"因为记忆坏了所以脚本跑不起来"不能忍；
* **什么时候写**：引擎每轮结束（`StoreManager.flush()`）和 `ctx.close()`，
  不是每次 `set` 都写盘；
* 写盘失败**不抛异常**（磁盘满不该把脚本弄挂），但会记 error，脏标记留着下次再试。

放 `data/` 而不是 `logs/`：`logs/` 是运行产物（会清、按次分目录），
记忆是下次开还要用的东西。

---

## 六、和事件流的关系

每次写入都会发一条 `store_changed` 事件（`{store, key, old, new}`），
落进 `logs/events/<功能>.jsonl`，界面的「记忆」面板也靠它刷新。

接线在 `gamebot/bootstrap.py`：仓库只认一个 `on_change` 回调，
**不认识"事件"这个概念** —— 状态层不该知道上层有事件流。

事件流本身见 `src/gamebot/events.py` 的模块 docstring。

---

## 七、什么时候**不要**用仓库

* 只在这一局里有意义（重试计数、当前进度）→ 黑板；
* 用户能调、跑的过程中不该变（刷几局、阈值）→ 运行参数；
* 需要强校验、需要中文标签、要进界面表单 → 运行参数 + `form.py`；
* 一步之内算完就扔 → 局部变量。

**仓库只解决一件事：让"下次开还在"变成一个显式、分仓、可删的动作。**
