# UI 设计（本地控制台）

一个跑在本机的图形界面，用来**选脚本、看画面、看日志、开始/停止**。
不做网页、不做远程 —— 它的用户就是坐在同一台机器前调脚本的人。

启动顺序是 **① 选软件（拿坐标）→ ② 选游戏 → ③ 选脚本 → 开始**，
每一步的依赖理由见第四节。

剩下没做的（都不影响"能跑"）：`events.py` 结构化事件流（第五节的独立日志
与更细的状态面板要用它）、画面标注、多脚本队列。见第十节。


## 二、技术选型

**推荐 PySide6（Qt6）**，作为可选依赖 `[ui]` 装，不进主依赖。**已按此实现。**

| 方案 | 优势 | 代价 |
|---|---|---|
| **PySide6**（推荐） | 控件齐（下拉框/表格/日志框/图像显示都有现成的）；`QThread` + 信号槽的线程模型和"引擎跑工作线程"天然契合；跨平台；LGPL | 装完约 150MB |
| Tkinter | 标准库，零依赖 | 图像显示要手搓（`PhotoImage` 慢、不缩放）；线程 + 界面互相等待容易卡死；深色主题难做 |
| 本地网页（FastAPI + 浏览器） | 界面随便写、图表好看 | 又多一套 Web 依赖；截图预览要走 base64/WebSocket，延迟和内存都不划算；调试时多一个进程状态要管 |
| Textual（终端 TUI） | 好看、轻 | 显示不了截图 —— 而看画面正是这个工具的核心 |

选 PySide6 的决定性理由是**要显示截图**：其余三个方案在这一点上都别扭。
第二个理由是**线程模型**：引擎必须在工作线程里跑，Qt 的信号槽是现成的、
经过检验的跨线程通信方式；Tkinter 做同一件事要靠 `after()` 轮询。

因为它是可选依赖，`import gamebot.ui` 失败时要给一句人话：

```
UI 依赖没装。执行: uv sync --extra ui
```

三块职责：

* **顶栏** —— 三步选择（软件 → 游戏 → 脚本）+ 动作。所有下拉框都来自注册表，不写死；
* **左上：三页** —— 状态 / 流程（**画出来的图 + 完整文字版**）、
  识图日志（**带红框的匹配图** + 结构化表格）、检查输出；
* **右侧：当前这一轮的数值** —— 当前/期望状态、节点、轮次、重定位，
  以及脚本规模、未认领状态、模板根、所选节点；
* **底部：日志大框** —— 占最大高度，`QSplitter` 可拖。

### 快捷键

| 键 | 动作 |
|---|---|
| `F5` | 开始运行 |
| `Esc` | 停止（毫秒级） |
| `F8` | 抓一张：截一帧并画出识别到的框 |
| `F6` / `Shift+F6` | 检查 / 自检 |
| `F7` | 重新检测可见软件窗口 |
| `Ctrl+1` / `Ctrl+2` / `Ctrl+3` | 切到「状态 / 流程」/「识图日志」/「检查输出」 |
| `F1` | 弹出这份清单 |

选键的考虑：`F5` 开始、`Esc` 停止沿用 IDE 和播放器的直觉（闭眼能按）；
`F8` 单键给"抓一张"，因为调识别时它按得最多；`Esc` 只在运行中有反应，
而下拉框弹窗开着时 `Esc` 先被下拉框吃掉（关弹窗），不会误触停止。

**三个"停止"入口**（按钮 / `Esc` / 关窗）都走同一个 `_on_stop`，
所以"没在跑时按 Esc"是安全的空操作。

实现上有一处值得记住的坑：**键位提示不能"启动时往 tooltip 后面追加一次"**。
「开始」那类按钮的 tooltip 是动态的（`set_runnable` 每换一次脚本就重设），
追加的那份会被下一次重设冲掉 —— 表现是"键位提示时有时无"。
所以提示登记进 `ControlsBar`，由它的 `_tip()` 统一拼，谁设 tooltip 都绕不过它。

没有做菜单栏：菜单要占一行高度，而这个界面宁愿把高度留给日志和带框的图。
快捷键本来就该"用熟了不用看"，需要看时按 `F1`。

### 每个东西只在一个地方显示

这条是改出来的，值得单独写：右侧面板原来还有一份「状态树 / 流程图 / 检查输出」
三页，和左边**是同一份数据**。后果有两个 —— 白占大半屏，而且
**同一份数据两处显示会让人以为是两份不同的东西**（"这两边不一样，哪个对？"）。

现在：能画成图的、能点的、需要宽的，全放左边三页；右侧只留"一眼看数值"的
短信息。谁都没有第二份。

### 左边为什么要"图 + 文字"两份，这不算违反上一条

图的职责是**形状**：谁连着谁、当前在哪一格、这条边有没有条件 —— 这些用文字
读不出来。文字的职责是**细节**：完整的状态 id、ROI 数值、边的优先级、
"这个状态有没有节点认领" —— 图里放不下，长 id 得省略号截断。

两者是**互补的两半**，不是同一份数据的两个副本；摆成上下两块、中间可拖，
一眼能同时看。所以：

* 文字那块的 `describe()` 直接调**状态层/流程层自己的** `tree.describe()` /
  `graph.describe()`，界面**不自己拼** —— 否则又会出现"界面说的"和
  "定义实际内容"两套说法；
* 文字块至少留 110px 高（约 5 行）。上一版它是被压扁的那块，
  结果 `PageTree` 只显示了前两行 —— 这就是"信息不全"的来源。

### 为什么**没有**实时画面

一开始做的是实时预览，用下来发现它回答不了真问题：同一帧上"首页 logo 在左上角
0.98"和"在右下角 0.91"在缩略图里**长得一样**，但一个是命中、一个是偶然相似。
实时画面只说明"屏幕现在什么样"，而调脚本要问的是：

1. **它认到的是哪一块？** → 把命中框画在图上，一眼看出圈对没有；
2. **没中的时候它在哪块里找？** → 把 ROI 也画出来，才能区分
   "圈错了"和"圈对了但阈值太高"；
3. **差多少分？** → 表格直接给分数。

所以画面没有删掉，而是**改成了"每次匹配留一张带框的图"**（见第六节）。
画框只用三种颜色，语义固定别再改：**红=命中、橙=未命中、蓝=搜索范围**。

细节约定：

* **三步是依赖顺序，不是排版**：坐标从窗口来（``WindowInfo.region`` 就是客户区
  原点），所以"选软件"必须排第一，而且选完立刻把坐标显示出来 ——
  它错了的表现是"每次点击都偏一个窗口位置"，看不见就没法发现；
* **按钮点了没用时置灰并写明原因**（`setToolTip(...)`），而不是点了没反应 ——
  后者会让人怀疑自己操作错了。**注意原因要写真的那一条**：引擎已经实现，
  所以置灰时必须写清"还缺什么"。**开始按钮现在已经不灰了** —— 接线做完了；
  剩下的置灰只有两种情况：没选脚本，或者运行中；
* 停止按钮在空闲时置灰；运行时"开始"置灰、"停止"变红；
* **抓一张**（手动）：截一帧，按当前脚本把每个状态的查询跑一遍，把框画出来存下。
  跑脚本之前用它确认"它到底认的是哪一块"；
* 图里**不自动顶回视角**：用户滚轮缩放/拖动过之后，每轮重画不再 reset ——
  否则运行中视角会一直被抢回去；
* 日志框用 `QPlainTextEdit`（不是 `QTextEdit`）—— 大量追加时快得多，且自带 `maximumBlockCount` 限制，不会越跑越吃内存；
* 级别用颜色区分（ERROR 红、WARNING 黄、DEBUG 灰），但**不要**用富文本拼 HTML —— 每行一次 `QTextCharFormat` 设置就够。

## 四、线程模型（这块最容易出错）

铁律：**引擎在工作线程里跑，任何控件只能由界面线程碰。** Qt 从别的线程改控件
不会立刻报错，而是随机崩溃 —— 这类 bug 极难查，所以从第一行代码就要守规矩。

```
界面线程                                引擎线程（QThread）
─────────                               ──────────────────
点「开始」
  ├ 装配：读配置 / 建 Session / 校验 / 查模板
  │   （失败要立刻弹给人看，所以留在界面线程）
  ├ worker.configure(ctx, engine)  ← 直连：只是赋值，必须先做完
  ├ 静音抓帧线程（预览要交给引擎那一帧）
  └ _engineTickRelay.triggered ──────▶ worker.run()
                                       └ engine.run(on_tick=…)
                                             ├ 每轮 emit TickEvent（值快照）
                                             └ 每 N 轮 emit QImage
  预览/状态面板 ◀──队列连接（自动排队）─────┘
点「停止」
  └ engine.stop()  ← 线程安全：设引擎标志 + 写 Session 上的中止标志
     引擎在 ctx.sleep / 等待 / 退避里被立刻唤醒（实测 10ms）
```

三个关键决定：

1. **停止按钮不杀线程**，只 `engine.stop()`。中止机制的单一事实源是 `Session`
   （`threading.Event`），所有等待循环都会毫秒级响应。
   `QThread.terminate()` 永远是错的 —— 它会在任意一条指令上杀掉线程，
   可能留下按了一半的键。

   ⚠️ **实测踩过的坑**：``engine.stop()`` 早期只设了引擎自己的标志位，
   没告诉 Session。那样循环要等**当前这一觉睡完**才看得到停止请求 ——
   而这一觉可能是节点声明的 ``cooldown``。表现就是"点了停止但脚本还在转"。
   现在两处都设：``_stop_reason`` 决定报告怎么写，Session 那边的标志决定
   能不能马上醒。实测（冷却 3s 的场景）总耗时从 3s+ 降到 0.31s。
2. **信号槽走队列连接**（跨线程默认就是），所以工作线程里 `emit` 是安全的，
   槽函数一定在界面线程执行。
3. **一轮结束才允许再次点开始**：worker 的 `finished` 信号里恢复按钮状态，
   并用一个 `_running` 标志防重入。

## 五、日志与事件流（两套东西，别混）

现在 `setup_logging()` 提供**控制台**和**文件**两个 handler：

| 需要的东西 | 现状 |
|---|---|
| 日志进界面 | ✅ `CallbackHandler` + `attach_handlers` |
| 事后补看（界面晚开也能看到之前的） | ✅ `RingBufferHandler`（最近 2000 条，`snapshot()`） |
| 逐步骤记录 | ✅ journal（JSONL，`logs/journals/<功能>.jsonl`） |
| 状态面板的数据 | ✅ 走 `EngineWorker.ticked` 的 `TickEvent`（见下） |
| 每次运行独立日志文件 | ❌ 只有一个总文件；要加 `logs/runs/<时间戳>.log` |

**最后一行是唯一还没做的**（属 `events.py` 的活）。

### 状态面板为什么不解析日志

日志是写给人看的（可读的中文句子，格式随时会改）；状态面板要的是字段
（当前状态、期望状态、节点、轮次、重定位）。用正则去抠日志文本，
等于把两种需求绑死 —— 改一次日志措辞界面就崩。

所以状态面板走的是**结构化值**：``EngineWorker`` 每轮发一个 ``TickEvent``
（frozen dataclass，见 ``ui/engine.py``）。它刻意只装值、不装引擎对象 ——
把引擎交给界面线程用，等于两个线程同时碰一个有状态对象。

```python
@dataclass(frozen=True, slots=True)
class TickEvent:
    tick: int
    page: str            # 当前状态（跟踪器的判断）
    overlays: tuple[str, ...]
    expected: str        # 流程层以为该在的状态
    node: str            # 当前节点
    confirmed: bool      # "连续几帧"够了没
    recoveries: int      # 重定位次数
    last_recovery: str
```

**``page`` 和 ``expected`` 分两个字段，是这块面板最要紧的设计**：
两者不一致的那一刻正是重定位发生的时候，而那是排查"它为什么跳了"
唯一要看的东西。合成一个字段就看不出来了。

（``events.py`` 仍然值得做，但理由变了：它是"每次运行独立日志 + 更细的
执行轨迹 + 以后接回放/训练数据"的数据源，不再是状态面板的前提。）


```python
# src/gamebot/events.py
class EventKind(StrEnum):
    RUN_STARTED = "run_started"
    FRAME = "frame"
    PAGE_CHANGED = "page_changed"
    NODE_ENTERED = "node_entered"
    DECISION = "decision"          # 含"没走成"的那次
    STEP_DONE = "step_done"
    RUN_STOPPED = "run_stopped"
    ERROR = "error"

@dataclass(frozen=True, slots=True)
class RunEvent:
    kind: EventKind
    at: float
    tick: int
    data: dict[str, Any]

class EventBus:
    """同步发布、同步回调。发布方（引擎/执行器）只管发，不管谁在听。"""
    def subscribe(self, fn: Callable[[RunEvent], None]) -> Callable[[], None]: ...
    def publish(self, event: RunEvent) -> None: ...
```

发布点（正好都是已有的返回值的搬运，不新增逻辑）：

| 事件 | 发布者 | data |
|---|---|---|
| `PAGE_CHANGED` | 引擎（`tracker.update` 返回非 None 时） | `PageChange.to_dict()` |
| `DECISION` | 引擎（`cursor.step` 返回后） | `Decision.to_dict()` |
| `RECOVERED` | 引擎（`_realign` 落下一次重定位后） | `Recovery.to_dict()` |
| `STEP_DONE` | 执行器 | `StepOutcome.to_dict()` |
| `RUN_STARTED` / `RUN_STOPPED` | 引擎 | `RunReport.to_dict()` |

`RECOVERED` 是这次架构改动新增的观察点：状态对不上时引擎会**自己挪游标**，
界面必须把它显示出来（"我以为在 A，实际在 B，已落到节点 C"），
否则用户看到的只是"它没按我选的节点走"。数据源是 `RunReport.recoveries`。

**状态面板现在已经能看到它了**（走 `TickEvent.recoveries` / `last_recovery`，
不需要等 `events.py`）。`events.py` 要做的是把这套东西**也**变成可落盘、
可回放的事件流，并且**每次运行一个独立日志文件**。

界面把 `RunEvent` 映射成状态面板字段；journal 顺手把它写成 JSONL ——
一份数据两个用途，不重复劳动。

日志那边的两个 handler **已经实现**（`utils/logging.py`）：
`RingBufferHandler`（环形缓冲，`snapshot()` 给晚开的界面补看）和
`CallbackHandler`（每条记录回调一次，界面在这里 emit 一个 Qt 信号），
配套 `attach_handlers` / `detach_handlers`。

**注意回收**：`CallbackHandler` 持有界面对象的引用，关窗时必须
`logger.removeHandler(...)` 并断开信号，否则界面对象不会释放（表现为关了窗还有后台线程在跑）。

## 六、识图记录：把「它认到的是哪一块」变成一张图

这一节是"删掉实时画面"换来的东西，也是调脚本时最常用的一件工具。

### 做法：包一层，而不是改 Matcher

```
Frame ──▶ Matcher（OpenCV）          算法只管算
             ▲
        _MatcherTap（记录 + 画框）    记录只管记
```

在 ``Matcher`` / ``TextReader`` 外面套一层透明包装（``vision/recorder.py``）。
好处是**这个 Session 上的所有查询都会被记下来**，不用在每个调用点插桩 ——
漏一个调用点就等于漏一段证据，而漏掉的那次往往正是出问题的那次。

原子层完全不知道"记录"这件事存在，性能和职责都不受影响；不装包装一切照旧。

### 框的坐标怎么换算回源坐标

``Matcher.match`` 只拿得到一个**图像数组**，它不知道这张图在源分辨率里的位置 ——
而 ROI 裁剪过的帧（``Frame.crop``）原点不是 0，框必须加上原点才画得对。

所以由 ``Frame`` 在查询前把"原点 + 帧号"写进一个 ``ContextVar``，包装层读：

```python
# atomic/frame.py
_mark_frame(self)          # -> vision.recorder.set_frame_context(x, y, frame_id)
```

用 ``ContextVar`` 而不是全局变量：它**每线程独立**，抓帧线程和引擎线程各查各的
不会互相串。也**没有**把这个参数加进 ``Matcher`` 的签名 —— 那等于让算法层知道
"记录"这件事存在，职责就混了。

### 一帧一张图，最多留 N 张

同一帧里查十几个模板是常事。如果每次匹配都存一张，20 张上限两帧就满了，
而且那十几张图彼此只差一个框，根本没法看。所以：

* **同一 ``frame_id`` 的记录攒在一起**，换帧（或 ``flush()``）时才落盘**一张**图，
  所有框画在同一张上；
* 留存上限 ``vision.record_keep``（默认 **20**），超出按修改时间删最旧的；
* **只删自己写的 ``match_*.png``** —— 手工截的图、界面快照都躺在同一个目录里，
  误删了比不清理更烦（有专门一条测试钉着）；
* 存图失败**绝不影响识图**（纯旁路，``try/except`` 吞掉并记 debug）。

### 配置

```yaml
vision:
  record: true        # 关掉就完全不记（也不存图）
  record_keep: 20     # 最多留几张带框的图
```

日志本身在内存里留最近 300 条（``RecognitionRecorder(history=…)``）——
调脚本要看的是"刚才那几次"，不是三个月前的。

### 同一个目录里躺着三类图，留存规则不能互相踩

``logs/screenshots/`` 里有三类文件，**都靠名字前缀区分**：

| 前缀 | 谁写的 | 留存 |
|---|---|---|
| ``match_*.png`` | 识图记录（本节） | ``vision.record_keep``，默认 20 |
| ``fail_*.png`` | 执行器存的失败帧 | 跟识图记录走（它的 5 倍，至少 20） |
| 其它 | 手工截图、界面快照、``gamebot capture`` | **永不自动删** |

清理共用一个 ``vision.recorder.prune_old(directory, pattern, keep)``，
**必须带 pattern** —— 这是这个函数唯一要紧的地方。不带 pattern 地"清最旧的几个"
会把用户手工截的图删掉，而那种损失比磁盘涨满更让人恼火。

前缀也不是装饰：``attach_frame`` 早期生成的名字是 ``t{attempts}_{step}.png``，
不带任何前缀 —— 于是"清理旧失败帧"那套规则**永远扫不到它**，
失败帧会无上限地涨，而且不报任何错。现在带上 ``fail_`` 前缀和轮次号。

### 失败帧：存了就必须能在日志里找到

``save_frames_on_error`` 有两个隐形的坑，都修了：

1. **帧在写 journal 之后才存** → 记录里没有文件名，你得自己去目录里按 tick 号翻。
   现在执行器在 ``_record`` 里**先存帧、再写 journal**，路径跟着那条记录一起落盘
   （JSONL 里的字段名是 ``frame``）；
2. **没有留存上限** → 跑一晚上、每轮都失败就是几千张全尺寸 PNG。现在有上限了。

这条路径原来生产代码里**没人调用** ``attach_frame``（只有测试调），
所以"存是存了、但对不上号"这件事一直没被发现 —— 现在有测试钉着。

## 七、「从哪个节点开始」—— 能做，而且很便宜

这是你问的那个。结论：**能做，底层已经完全支持了，缺的只是界面把参数接上。**

`GraphCursor` 本身就是个普通 dataclass，`current` 是字段：

```python
@dataclass
class GraphCursor:
    graph: Graph
    current: NodeId = ""        # 空 = 从 graph.initial 开始
```

所以"从 `fight` 开始"就是 `GraphCursor(graph, current="fight")`，
或者 `engine.cursor.current = "fight"`。

**底层三件小事现在都做完了**，剩下的只有 UI 把参数接上去：

1. ✅ `FlowEngine.__init__(..., start_node: NodeId = "")` —— 收参数、校验节点存在
   （不存在直接抛 `FlowError`）、传给游标，`run()` 里的 `cursor.reset(to=start_node)`
   也跟着它（否则"从 X 开始"会在第一次 reset 后悄悄丢掉）；
2. ✅ `GraphCursor.reset(to=...)` 可以回到**配置的起点**，不再只能是 `graph.initial`；
3. ✅ 界面已经有起始节点下拉框（从 `scenario.graph.nodes` 取）；缺的是把它
   传进 `FlowEngine` 并让 worker 真的跑起来。

### 三种语义，得选一个

"从节点 X 开始"有歧义：**游戏此刻是不是已经在 X 那个状态上？** 三种做法：

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| **A. 假定已在** | `cursor = X`，同时 `tracker.set_initial(X.page)` | 立刻开始，没有等待 | 选错了会被**重定位**到真实状态对应的节点（不是原地不动，也不会乱点）—— 用户会看到"它没按我选的节点跑"，报告里有 `recoveries` 可查 |
| **B. 等它出现**（推荐） | `cursor = X`，tracker 保持"未知" | 自我同步，选错最多是等（有 `unknown_grace` 和超时） | 要多等一两轮识别 |
| **C. 强制** | 同 A，但跳过状态校验与重定位 | 不会被挪走 | **危险** —— 可能在不该点的状态上乱点 |

推荐 **B 为默认，A 做成一个勾选项**「假定游戏已在该状态（跳过等待）」。
理由：A 的失败模式对调试的人来说很难自己看出来，而 B 最坏也只是慢一点。C 不要做。

另外：如果 X 的 `page` 是 `None`（纯逻辑 / 纯等待节点），A 和 B 就没区别了。

### 顺带三个要注意的点

* **状态校验仍然生效，但表现形式变了。** 从 X 开始不代表"跳过所有检查"：
  实测状态和 X 声明的 `page` 不符时，本轮**一个动作都不执行**，引擎会先走
  重定位（慢路径找回真实状态 → 关联表查出该去哪个节点 → 游标挪过去）。
  这是设计要的效果，不是 bug —— 界面必须把它显示出来
  （"重定位：节点 fight 期望 home/battle，实测 home → 落到节点 lobby"），
  否则用户只会看到"它没按我选的节点走"。数据源是 `RunReport.recoveries`。
* **计数从零开始。** `visits` / 冷却 / 边的 `max_times` 都是新的，
  所以从中间开始不会被"之前已经访问过 N 次"限制住。调试时这是好事。
* **这是它最大的价值。** 想测"战斗结束"那条分支，不用真的从头把游戏玩到那一步 ——
  直接把游戏手动摆到那个状态，选对应节点，点开始。
  没有这个功能，调一条后期分支的成本是"每次重跑整个流程"。

### 还需要一个东西：「解除守卫」的调试开关（可选，阶段 3）

真正的调试场景里还有一种是"我想看它在这个状态上会点什么，但我的识别条件还没调准"。
这时候状态校验反而碍事。可以加一个**显式的**调试开关
「忽略状态校验（危险）」—— 需要在界面上打勾 + 二次确认，
并且运行时顶部横幅常驻红字提示。默认关，不跨会话记忆。
**注意它同时也要关掉重定位**，否则引擎会先把游标挪到真实状态对应的节点上，
"在这个状态上会点什么"根本看不到。

## 十、做完之后回填的几条经验

这几条都是**实际跑起来才暴露**的，写在这里比写在代码注释里更容易被下次看到。

**① 字体必须带中文兜底。** 一开始 `MONO_FONT = "Consolas"` —— Consolas
没有中文字形，日志里的中文全变方框。改成 `QFont.setFamilies([...])`
给一串候选（Consolas → 雅黑），Qt 按顺序回退，于是"数字等宽对齐 + 中文正常"
同时成立。**所有硬编码字体名的地方都要留 CJK 兜底。**

**② 离屏渲染看不到真字体。** `QT_QPA_PLATFORM=offscreen` 的插件没有字体库，
中文全是方框，而且会打一句 "Qt no longer ships fonts"。所以截图自检要分两种：
离屏跑（验证能不能构造出来）和用真实平台插件跑（验证排版和字体）。
后者在有人登录的桌面上才能用。

**③ `uv run` 启动的 console script，`sys.path[0]` 不是当前目录。**
它是虚拟环境的 `Scripts/` —— 于是项目根下的 `games/` 导不进来，
界面上"脚本列表"是空的。`registry._import_games()` 里补了一次 cwd 再试，
并且把失败原因原样显示在界面上（而不是只留个空白下拉框）。

**④ 跨线程的东西一律在工作线程里创建。** 这个坑踩了一半就绕开了：
`mss` 的实例是**线程局部**的，在界面线程 new、在工作线程 capture 会出问题。
所以 `Session` 的建和关都在 `CaptureWorker.configure` / `shutdown` 里做。

**⑤ Qt 的信号宁可少连一次。** 界面上出现过"每条日志显示两遍" ——
`LogView` 在自己构造时接了 `recordArrived`，`MainWindow._wire()` 里又接了一次。
还有一个同类问题：`setCurrentIndex` 写在 `blockSignals(False)` 之后，
导致多 emit 一次 `currentIndexChanged`，抓屏会话白建一遍（先建后立刻被替换）。

**⑥ "提前 return"会漏掉副作用。** 选「不选脚本」时 `_on_script_changed`
在 `entry is None` 分支里直接 return 了，忘了重建抓屏会话 ——
表现是"切了脚本画面没变"，而且看起来像抓屏坏了。

**⑦ 拿错类型 + 返回 None = 静默少画东西。** 画状态树时写成
`for child_id in tree.children_of(pid): tree.get(child_id)` —— 而
`children_of` 返回的是 **Page 对象不是 id**，`get` 查不到就返回 `None`，
整棵子树于是**静默地**没画出来。界面不报错，只是少了一大截，
这种最难发现。教训：**循环变量名带 `_id` 就要确认它真的是 id**，
而"查不到"的分支至少要记一条日志。

**⑧ 在"控件还没布局"的时候算几何 = 算出一个荒谬的值。** 状态图的自动适配
在构造期执行，那时 `viewport()` 只有 96x26，于是整张图被缩成一枚邮票 ——
同样不报错。现在标成"待适配"，等 `showEvent` 里有真实尺寸再算。

**⑨ "两头都测过了"不等于"这条线通"。** 最典型的一次：`_start_engine_thread`
里创建的是 `_engineTickRelay`，而 `_on_start` / `_on_stop` / `closeEvent` 里
写成了 `_engine_tick_relay`（加下划线那种拼法）。同一个文件里两种命名风格并存，
**点「开始」直接 AttributeError** —— 而 517 个用例全绿，因为：

* `_SignalRelay` 本身有测试；
* 引擎在工作线程里跑也有测试（直接调 `EngineWorker`）;
* 但**没有任何测试点过界面上那个按钮** —— 信号连接、按钮 → 槽、跨线程这条路，
  全是"两头各自测过、连起来没验过"。

现在有 `tests/test_ui_run.py`：造一个假脚本（配置走假后端、模板检查打桩），
真的调 `_on_start` / 点 `start_btn` / 点 `stop_btn` / 跑到一半 `close()`。
把那个拼写错误塞回去，这些用例立刻变红 —— 验过。

**教训**：跨层、跨线程的"连线"必须有一条端到端用例。单元测试覆盖两头，
替代不了它。
