# UI 设计（本地控制台）

一个跑在本机的图形界面，用来**选脚本、看画面、看日志、开始/停止**。
不做网页、不做远程 —— 它的用户就是坐在同一台机器前调脚本的人。

## 一、先看现状：哪些能用了，哪些还是桩

设计 UI 之前必须把这条分清，否则会设计出一堆点不动的按钮。

| 能力 | 状态 | UI 能不能用 |
|---|---|---|
| 配置加载 / 校验 | ✅ 完成 | 能用 |
| 窗口枚举（找 `window_title`） | ✅ 完成，真机验证 | 能用 |
| 截屏 + 区域裁剪 + 坐标换算 | ✅ 完成，真机验证（2560x1440） | **能用** |
| 模板匹配（OpenCV） | ✅ 完成，真机验证 | 能用 |
| 原子层 L0~L5（50 个方法） | ✅ 完成 | 能用 |
| 可中止的等待 | ✅ 完成，实测 0.1ms 响应 | **能用（停止按钮靠它）** |
| 页面树 / 跟踪层 / 校验 | ✅ 完成 | 能用 |
| 流程图 / 游标 / 决策 / 校验 | ✅ 完成 | 能用 |
| 脚本注册表（选游戏 / 选脚本） | ✅ 完成（`games.list_scripts()`） | **能用** |
| `check` / `selftest` | ✅ 完成（8 项自检全过） | **能用** |
| **`PageTree.locate()`** | ❌ 桩 | 不能 —— 认不出"现在在哪一页" |
| **`FlowEngine.tick()`** | ❌ 桩 | 不能 —— 没有任何一轮会执行 |
| 9 个 Step 的 `run()` | ❌ 桩 | 不能 —— 步骤本体没实现 |
| `Executor.run` / journal 落盘 | ❌ 桩 | 不能 |
| YAML 脚本加载 | ❌ 桩 | 用不了 YAML，只能手写 Python |
| OCR | ⚠️ 代码写了，没验证（依赖没装） | 不能依赖 |

**结论：`看图`这条链是通的，`看图之后做决定、动手`这条链还是桩。**

所以 UI 分两阶段做，第一阶段**今天就能全部可用**：

* **阶段 1（不碰引擎）**：选游戏/脚本、看页面树与流程图、跑 check/selftest、
  **实时画面预览**、日志大框；
* **阶段 2（等 `locate` + `tick`）**：开始/停止、起始节点、状态面板。

这样第一阶段不是"假的待办界面"，而是真的能帮上忙的工具 ——
调脚本时最花时间的本来就是"我截到的到底是不是我以为的画面"。

## 二、技术选型

**推荐 PySide6（Qt6）**，作为可选依赖 `[ui]` 装，不进主依赖。

| 方案 | 优势 | 代价 |
|---|---|---|
| **PySide6**（推荐） | 控件齐（下拉框/表格/日志框/图像显示都有现成的）；`QThread` + 信号槽的线程模型和"引擎跑工作线程"天然契合；跨平台；LGPL | 装完约 150MB |
| Tkinter | 标准库，零依赖 | 图像显示要手搓（`PhotoImage` 慢、不缩放）；线程 + 界面互相等待容易卡死；深色主题难做 |
| 本地网页（FastAPI + 浏览器） | 界面随便写、图表好看 | 又多一套 Web 依赖；截图预览要走 base64/WebSocket，延迟和内存都不划算；调试时多一个进程状态要管 |
| Textual（终端 TUI） | 好看、轻 | 显示不了截图 —— 而看画面正是这个工具的核心 |

选 PySide6 的决定性理由是**要显示截图**：其余三个方案在这一点上都别扭。
第二个理由是**线程模型**：引擎必须在工作线程里跑，Qt 的信号槽是现成的、
经过检验的跨线程通信方式；Tkinter 做同一件事要靠 `after()` 轮询。

因为它是可选依赖，`import gamebot.ui` 失败时要给一句人话：

```
UI 依赖没装。执行: uv sync --extra ui
```

三块职责：

* **顶栏** —— 选择与动作。所有下拉框都来自注册表，不写死；
* **左中：画面 + 状态** —— 画面是"我看到的是不是我以为的"，状态是"我现在在哪、刚做了什么"；
* **底部：日志大框** —— 占最大高度，`QSplitter` 可拖。

细节约定：

* 顶栏三个下拉框**联动**：换游戏 -> 刷新脚本列表 -> 换脚本 -> 刷新起始节点列表（从图的节点里取）；
* **未实现的按钮置灰并写明原因**（`setToolTip("需要 PageTree.locate()，尚未实现")`），
  而不是点了没反应 —— 后者会让人怀疑自己操作错了；
* 停止按钮在空闲时置灰；运行时"开始"置灰、"停止"变红；
* 日志框用 `QPlainTextEdit`（不是 `QTextEdit`）—— 大量追加时快得多，且自带 `maximumBlockCount` 限制，不会越跑越吃内存；
* 级别用颜色区分（ERROR 红、WARNING 黄、DEBUG 灰），但**不要**用富文本拼 HTML —— 每行一次 `QTextCharFormat` 设置就够。

## 四、线程模型（这块最容易出错）

铁律：**引擎在工作线程里跑，任何控件只能由界面线程碰。** Qt 从别的线程改控件
不会立刻报错，而是随机崩溃 —— 这类 bug 极难查，所以从第一行代码就要守规矩。

```
界面线程                          工作线程（QThread）
─────────                         ──────────────────
点「开始」
  ├ 关闭 UI 上的输入控件
  ├ 造 RunContext / FlowEngine
  ├ worker = EngineWorker(engine) ──moveToThread──▶ run()
  └ connect(worker.finished, ...)                   ├ engine.run()
                                                    ├ 每次状态变化 emit 信号
  日志框.appendRecord ◀──队列连接（自动排队）────────┤ logging 记录
  状态面板更新        ◀──队列连接────────────────────┤ engine 事件
点「停止」                                          │
  └ ctx.request_stop()  ←── 线程安全，写在 Session 上 ─┘
     引擎在下一个检查点抛 Cancelled（实测 0.1ms）
```

三个关键决定：

1. **停止按钮不杀线程**，只 `ctx.request_stop()`。中止机制的单一事实源是 `Session`，
   已经做好了（`threading.Event`），所有等待循环都会毫秒级响应。
   `QThread.terminate()` 永远是错的 —— 它会在任意一条指令上杀掉线程，
   可能留下按了一半的键。
2. **信号槽走队列连接**（跨线程默认就是），所以工作线程里 `emit` 是安全的，
   槽函数一定在界面线程执行。
3. **一轮结束才允许再次点开始**：worker 的 `finished` 信号里恢复按钮状态，
   并用一个 `_running` 标志防重入。

## 五、日志与事件流（两套东西，别混）

现在的 `setup_logging()` 只有**控制台**和**文件**两个 handler，
UI 需要的三样都没有：

| 需要的东西 | 现状 | 要加的 |
|---|---|---|
| 日志进界面 | 无 | 一个把记录推进内存的 `logging.Handler` |
| 事后补看（界面晚开也能看到之前的） | 无 | 环形缓冲（最近 2000 条） |
| 每次运行独立日志文件 | 只有一个总文件 | `logs/runs/2025-01-01_120341.log` |
| 状态面板的数据 | 无 | **结构化事件流** |

**最后一行是重点：不要靠解析日志文本来更新状态面板。**

日志是写给人看的（可读的中文句子，格式随时会改）；状态面板要的是字段
（当前页面、节点、轮次、决策）。用正则去抠日志文本，等于把两种需求
绑死在一起 —— 改一次日志措辞界面就崩。

所以要加一个事件流：

```python
# src/gamebot/events.py
class EventKind(StrEnum):
    RUN_STARTED = "run_started"
    FRAME = "frame"
    PAGE_CHANGED = "page_changed"
    NODE_ENTERED = "node_entered"
    DECISION = "decision"          # 含"没走成"的那次
    STEP_DONE = "step_done"
    RUN_STOPPED = "run_stopped"
    ERROR = "error"

@dataclass(frozen=True, slots=True)
class RunEvent:
    kind: EventKind
    at: float
    tick: int
    data: dict[str, Any]

class EventBus:
    """同步发布、同步回调。发布方（引擎/执行器）只管发，不管谁在听。"""
    def subscribe(self, fn: Callable[[RunEvent], None]) -> Callable[[], None]: ...
    def publish(self, event: RunEvent) -> None: ...
```

发布点（正好都是已有的返回值的搬运，不新增逻辑）：

| 事件 | 发布者 | data |
|---|---|---|
| `PAGE_CHANGED` | 引擎（`tracker.update` 返回非 None 时） | `PageChange.to_dict()` |
| `DECISION` | 引擎（`cursor.step` 返回后） | `Decision.to_dict()` |
| `STEP_DONE` | 执行器 | `StepOutcome.to_dict()` |
| `RUN_STARTED` / `RUN_STOPPED` | 引擎 | `RunReport.to_dict()` |

界面把 `RunEvent` 映射成状态面板字段；journal 顺手把它写成 JSONL ——
一份数据两个用途，不重复劳动。

日志那边加两个 handler：

```python
class RingBufferHandler(logging.Handler):
    """保留最近 N 条记录，界面晚开也能补看。"""
    def snapshot(self) -> list[logging.LogRecord]: ...

class CallbackHandler(logging.Handler):
    """每条记录回调一次。界面在这里 emit 一个 Qt 信号。"""
```

**注意回收**：`CallbackHandler` 持有界面对象的引用，关窗时必须
`logger.removeHandler(...)` 并断开信号，否则界面对象不会释放（表现为关了窗还有后台线程在跑）。

## 六、「从哪个节点开始」—— 能做，而且很便宜

这是你问的那个。结论：**能做，而且底层已经支持了，几乎不用改东西。**

`GraphCursor` 本身就是个普通 dataclass，`current` 是字段：

```python
@dataclass
class GraphCursor:
    graph: Graph
    current: NodeId = ""        # 空 = 从 graph.initial 开始
```

所以"从 `fight` 开始"就是 `GraphCursor(graph, current="fight")`，
或者 `engine.cursor.current = "fight"`。今天就能这么用。

要补的只有三件小事：

1. `FlowEngine.__init__(..., start_node: NodeId = "")` —— 收参数、校验节点存在（不存在直接报错，
   而不是跑起来才发现"原地不动"）、传给游标；
2. `GraphCursor.reset()` 现在回到 `graph.initial`，要改成回到**配置的起点**；
3. UI 从 `scenario.graph.nodes` 取节点列表填下拉框（`describe()` 里已有这些信息）。

### 三种语义，得选一个

"从节点 X 开始"有歧义：**游戏此刻是不是已经在 X 那个页面上？** 三种做法：

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| **A. 假定已在** | `cursor = X`，同时 `tracker.set_initial(X.page)` | 立刻开始，没有等待 | 选错了会**沉默不动**（位置守卫生效，这是对的，但用户会困惑） |
| **B. 等它出现**（推荐） | `cursor = X`，tracker 保持"未知" | 自我同步，选错最多是等（有 `unknown_grace` 和超时） | 要多等一两轮识别 |
| **C. 强制** | 同 A，但跳过位置守卫 | 不会沉默 | **危险** —— 可能在不该点的页面上乱点 |

推荐 **B 为默认，A 做成一个勾选项**「假定游戏已在该页面（跳过等待）」。
理由：A 的失败模式（什么都不做）对调试的人来说很难自己看出来，
而 B 最坏也只是慢一点。C 不要做。

另外：如果 X 的 `page` 是 `None`（纯动作节点，不绑定页面），A 和 B 就没区别了。

### 顺带三个要注意的点

* **位置守卫仍然生效。** 从 X 开始不代表"跳过所有检查"：
  实测页面和 X 声明的 `page` 不符时，**动作一个都不会执行**。这是设计要的效果，
  不是 bug —— 界面要把它显示出来（"节点 fight 期望页面 home/battle，
  实测是 home —— 已等待 3.2s"），否则用户只会看到"它不动"。
* **计数从零开始。** `visits` / 冷却 / 边的 `max_times` 都是新的，
  所以从中间开始不会被"之前已经访问过 N 次"限制住。调试时这是好事。
* **这是它最大的价值。** 想测"战斗结束"那条分支，不用真的从头把游戏玩到那一步 ——
  直接把游戏手动摆到那个状态，选对应节点，点开始。
  没有这个功能，调一条后期分支的成本是"每次重跑整个流程"。

### 还需要一个东西：「解除守卫」的调试开关（可选，阶段 3）

真正的调试场景里还有一种是"我想看它在这个页面上会点什么，但我的识别条件还没调准"。
这时候位置守卫反而碍事。可以加一个**显式的**调试开关
「忽略页面守卫（危险）」—— 需要在界面上打勾 + 二次确认，
并且运行时顶部横幅常驻红字提示。默认关，不跨会话记忆。

## 八、分阶段落地

只能靠 `gamebot capture` 存盘再看 —— 有个实时画面 + 日志框会舒服很多。
